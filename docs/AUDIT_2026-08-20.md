# YH Connect — Full Codebase Audit (2026-08-20)

Scope: entire codebase, read-only, across five parallel passes — backend
security, backend completeness/correctness, admin frontend, client frontend,
talent frontend + shared infra (chat, nav, auth). Each pass first read
`docs/PROJECT_STATUS.md` and `docs/BUG_FIXES_2026-08-16.md` and was told not
to re-report anything already documented as fixed there unless a re-check
showed it was actually still broken. Findings below are net-new or
confirmed-still-open only.

Baseline health at time of audit: **17/17 backend tests pass**, **`tsc
--noEmit` clean**, **single Alembic head, local DB at head, no model/migration
drift**.

## Priority findings

### High

1. **Legacy `POST /api/v1/messages` bypasses project-membership authorization**
   `backend/app/api/v1/messages.py:184-207` (`send_message`, mounted via
   `legacy_router`). When `payload.project_id` is omitted, this endpoint skips
   the participant checks that the newer `/projects/{id}/messages` endpoint
   enforces, and creates a message straight from the caller to any
   `recipient_id` in the body. Any authenticated user can message any other
   user directly, reopening the exact class of bug already fixed on the main
   messaging route.
   **Fix**: require `project_id` and run the same participant checks here, or
   remove the legacy route from `router.py` if the frontend no longer needs it.

2. **`confirm_project` / `complete_project` don't block on milestone-scoped disputes**
   `backend/app/api/v1/projects.py:275,319`, `backend/app/services/disputes.py:63`
   (`has_blocking_dispute`). Called with `milestone_id=None`, the guard
   `d.milestone_id is None or d.milestone_id == milestone_id` only matches
   project-general disputes — a dispute scoped to a specific (even already-paid)
   milestone never blocks completion. A client can confirm/complete a project
   (unlocking reviews) while an open milestone-specific dispute sits
   unresolved.
   **Fix**: add an "any open dispute on this project" check (ignore
   `milestone_id` scoping) and use it in both `complete_project` and
   `confirm_project`.

### Medium

3. **`SECRET_KEY` defaults to a hardcoded value with no production guard**
   `backend/app/core/config.py:16` (`"dev-secret-change-me"`). If unset in a
   real deployment, JWTs (including admin tokens) can be forged by anyone who
   knows the default. No startup check enforces overriding it.
   **Fix**: refuse to boot outside dev if `SECRET_KEY` is still the default.

4. **No production guard on Monnify/VerifyMe being unconfigured**
   `backend/app/services/monnify.py`, `backend/app/services/nin_verification.py`,
   `backend/app/api/v1/wallet.py:80-85`. This is a deliberate dev convenience
   (simulate payments/KYC when keys are unset) but there's no startup
   assertion forcing real keys in production — if ops ever deploys without
   them, wallet top-ups become free money and any well-formed NIN
   auto-verifies to Tier 2.
   **Fix**: loud startup warning/refusal-to-boot outside dev when these keys
   are unset.

5. **`partial_split` / `no_action` dispute outcomes don't move or reserve money**
   `backend/app/api/v1/disputes.py:212-224`, surfaced in
   `src/app/admin/disputes/[id]/page.tsx:28`. Resolving with these outcomes
   clears the dispute's blocking status but leaves the milestone `funded`/
   `approved` — the professional can then claim the **full** amount through
   the ordinary release endpoint, silently defeating an admin's "partial
   split" decision. Not a stuck state, just an unenforced one.
   **Fix**: implement real partial disbursement, or remove `partial_split`
   from the selectable outcomes until it is implemented; require an explicit
   fund decision on `no_action` too.

6. **Admin wallet-adjustment has no upper-bound guard or confirmation**
   `src/components/admin/AdjustWalletDialog.tsx:28-42`,
   `backend/app/api/v1/admin.py:220-262`. Only rejects zero/NaN/negative-past-
   balance; no sanity cap, no `confirm()` step, unlike every other
   money/state-changing admin action in the panel.
   **Fix**: add a client-side confirm step (and a sanity-threshold warning)
   before submit.

7. **`InviteToProjectDialog` wallet-balance warning fires at the wrong step**
   `src/components/site/pages/DashboardPages.tsx:1601-1610`. Compares the
   invite's proposed amount to the client's wallet balance and shows a
   blocking-looking "fund wallet" warning — but sending an invite never
   touches escrow; funding only happens later at milestone creation (where the
   correct version of this warning already exists in `ProjectWorkspace.tsx`).
   Can needlessly discourage a client from sending a valid invite.
   **Fix**: remove the warning here (or reword as informational, non-blocking).

8. **Suspend/reactivate user and "Send Announcement" fire with no confirmation**
   `src/app/admin/users/page.tsx` / `[id]/page.tsx` (`toggleActive` /
   suspend button), `src/app/admin/page.tsx` (`AnnouncementDialog.submit`).
   Suspension immediately kills the user's active sessions; the announcement
   broadcasts to every active user platform-wide by email + in-app — the
   highest-blast-radius action in the admin panel, yet the least friction.
   Inconsistent with dispute-resolve/force-cancel/CMS-delete, which all use
   `confirm()`.
   **Fix**: add `confirm()` (announcement: ideally show recipient count) to
   both.

### Low

9. Rate limiting missing on `reset-password`, `verify-email`,
   `resend-verification`, `change-password`, and NIN/KYC submission
   (`backend/app/api/v1/auth.py`, `clients.py`, `verification.py`) — only
   register/login/forgot-password are throttled today. Worst case today is an
   email-bomb via `resend-verification` or scripted NIN-name probing.
10. Public `GET /professionals/{id}` leaks `bank_code` on an unauthenticated
    endpoint (`backend/app/schemas/profile.py` `ProfessionalOut`). Should be
    owner-only.
11. `POST /uploads` has no rate limit — repeatable 10MB uploads from any
    authenticated user is a disk-fill DoS vector.
12. `cors_origins` silently falls back to `["*"]` (with credentials allowed)
    on a malformed `BACKEND_CORS_ORIGINS` env var instead of failing closed
    (`backend/app/core/config.py:79-83`).
13. OpenAPI docs (`/docs`, `/openapi.json`) always enabled, no env gate —
    minor info disclosure, not a vulnerability by itself.
14. Admin force-cancel still doesn't auto-refund escrow on funded/approved
    milestones (`backend/app/api/v1/admin.py:355`) — re-confirmed still true;
    already logged as a deliberate not-yet-decided gap in
    `BUG_FIXES_2026-08-16.md`.
15. `resolve_dispute` reads `milestone.status.value` without a None-check
    (`backend/app/api/v1/disputes.py:213-220`) — not reachable today (no
    milestone hard-delete exists), but would raise `AttributeError` if that
    invariant is ever broken.
16. Admin disputes list fetches the entire dataset and paginates client-side,
    unlike every sibling list page's server-side pagination — fine at current
    volume, won't scale.
17. Talent `ApplyDialog` only checks the proposal amount is non-empty, not
    `> 0`, client-side — backend correctly rejects with 400, so this is just
    an extra round-trip instead of instant feedback.
18. `RoleSwitcher`'s hard-navigation fix always lands on the new role's
    dashboard root, dropping any deep-link/query-param context — reasonable
    tradeoff, flagged since it was explicitly in scope to check.

## Test coverage gaps (confirmed by inspection, `backend/tests/`, 17 tests total)

No coverage at all for: talent tiers / proposal & concurrent-project caps,
certification badge review flow, reviews endpoint, admin wallet adjustments,
`Milestone.created_by` / professional-proposed milestones, the `review`
project status and its `complete`/`confirm`/`reopen`/`closing-note`
endpoints, and — notably — dispute **resolution outcomes** (existing tests
never actually call `PATCH /disputes/{id}` with `outcome=refund_client` or
`release_professional`, which is exactly why finding #5 above wasn't caught).

## What was verified solid (not just re-reported from prior docs)

- JWT/session handling: fixed alg, token-version invalidation on
  logout/password-change/suspend, bcrypt hashing, reset/verification tokens
  are random 256-bit and stored only as hashes.
- Double-hiring guard, negative-amount rejection, and the full
  fund→submit→approve→release/refund milestone state machine (including the
  belt-and-braces "was this milestone actually funded" check on release) are
  all intact and traced end to end — no double-pay path found.
- `PATCH /projects` mass-assignment fix (status/assigned_professional_id/
  progress stripped for non-admins) intact.
- Upload handling: real magic-byte sniffing, UUID filenames (no path
  traversal), size cap.
- No raw SQL string interpolation, no `eval`/`exec`/`os.system` anywhere
  reachable from the API.
- Mass-assignment reviewed across every `Update`/`Patch` schema — no
  privileged fields (`role`, `is_verified`, `kyc_status`, `wallet_balance`)
  are client-writable.
- Webhook signature verification (HMAC-SHA512) plus replay protection
  (no-op on already-successful transaction) on the Monnify webhook.
- Migrations vs. models: zero drift, single Alembic head, verified by diffing
  `PRAGMA table_info` against every touched model.
- Notification coverage matches every event the frontend actually surfaces —
  no gaps found beyond what's separately listed above.
- Admin panel: every `/admin/*` route is guarded both client-side
  (`useAuthGuard("admin", ...)`) and server-side (`require_role(UserRole.admin)`
  on all 16 admin endpoints); no dead `api.ts` calls, no placeholder/mock data,
  no divide-by-zero in the new analytics charts.
- Client and talent journeys traced end to end (register → post/apply →
  fund/hire → milestone work → payment → final review → reviews) with every
  `api.ts` call cross-checked against backend schemas — no mismatches, no
  silent-failure buttons, no unhandled `JSON.parse` on stored drafts.
- Tier system is genuinely invisible to clients: grepped every frontend
  `tier` usage, confirmed it only renders behind the talent-role and admin
  layouts, never on the public professional view or any client-facing bid
  data.
- `ProjectChat` consolidation is real (no leftover duplicate chat
  implementations), unread-count logic has no self-counting or leak bugs,
  and tier-based proposal/concurrent-project limits surface specific,
  readable error messages (not generic toasts) on the frontend.

## Suggested next steps (priority order)

1. Fix the legacy messaging IDOR (#1) and the dispute-blocking gap on project
   completion (#2) — both are real, currently-exploitable correctness/security
   issues.
2. Decide on `partial_split` (#5): implement or remove it, and add test
   coverage for dispute resolution outcomes.
3. Add confirmation steps to wallet adjustment, user suspend, and send
   announcement (#6, #8) — cheap, closes off the panel's biggest
   blast-radius-vs-friction mismatches.
4. Add a production boot-guard for `SECRET_KEY` and Monnify/VerifyMe config
   (#3, #4) before any real production deploy.
5. The rest (#7, #9-18) are low-severity polish, worth batching into a normal
   cleanup pass.
