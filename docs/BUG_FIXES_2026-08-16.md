# YH Connect — Audit & Bug Fixes (2026-08-16)

Full code-level audit of the backend (all routers, services, models, schemas) and
frontend (stores, hooks, page components). Every change below is **backend-only**;
no frontend files were touched. All changes are uncommitted in the working tree,
alongside the pre-existing message-replies/tiers work.

Scope notes:
- Frontend `tsc --noEmit` passes clean (after clearing a stale `.next/` build
  cache, which had a corrupted generated `routes.d.ts`).
- All backend files pass `python -m py_compile`.
- The existing backend test suite (`backend/tests/`) does not touch any of the
  changed flows (messaging, bid acceptance, email verification), so it should
  stay green; run it to confirm.

## 1. Messaging authorization holes — `backend/app/api/v1/messages.py`

### Bug
`POST /projects/{project_id}/messages` had **no participant check at all**. Any
authenticated user could read a project id and a user id off the public browse
endpoints, then post messages into any project's thread (spam, impersonation
adjacent, harassment, or just noise). The WebSocket connect gate and the GET
thread endpoint already restricted access to project parties, so this was an
inconsistency that made the whole channel effectively open.

Two adjacent bugs in the legacy router:
- `POST /messages/{id}/read` crashed with an unhandled 500 when the message id
  did not exist (`_to_out(None)`), and returned the full message content to any
  caller who knew a message id, even non-participants.
- `POST /projects/{project_id}/messages/read` let any user mark *other people's*
  messages as read on any project.

### Fix
- Added `_is_project_messaging_party()` / `_require_project_messaging_party()`:
  participants are the client, the assigned professional, and any professional
  who bid on or was invited to the project (so a client can still vet bidders
  before hiring — that flow is preserved).
- Added `_require_recipient_is_project_participant()`: a message may be
  addressed to the client, the assigned professional, or (only when the sender
  is the client) a bidder/invitee being vetted. Nobody outside the participant
  set can be reached.
- Applied the same gate to the WebSocket connect handler (bidders now get live
  push instead of falling back to 30s polling) and to the legacy `send_message`.
- `mark_read` (legacy): 404 when the message is missing, 403 when the caller is
  neither sender nor recipient, and it only marks read when the caller *is* the
  recipient.
- `mark_thread_read`: 404 for unknown project, 403 for non-participants.

### Why it matters
This was the highest-severity finding: a missing authorization check on a
user-facing, two-way communication channel. Any account could post into any
conversation.

## 2. Double-hiring via bid acceptance — `backend/app/api/v1/bids.py`

### Bug
`PATCH /bids/{id}` with `status: accepted` did not check whether the project
already had an accepted proposal. A client could accept bid A (professional A
assigned, project moves to `in_progress`), then accept bid B: B was assigned,
A was silently displaced, and every later milestone payout
(`release_milestone_payout` → `disburse_milestone`) would go to B. A could
already be mid-work on funded milestones when the rug was pulled.

### Fix
Accepting now rejects with 400 ("This project already has an accepted proposal")
when the project has a different assigned professional. Re-accepting the same
bid stays a no-op (the check compares against the bid's own professional).

### Why it matters
Money-flow integrity: milestone escrow payouts are keyed to
`project.assigned_professional_id`, so allowing that to flip outside the
hiring flow could pay the wrong person.

## 3. Unvalidated `category_id` → poisoned rows → 500s on list endpoints

### Bug
`create_project`, `register_professional`, `become_talent`, and the
professional profile update path accepted any `category_id`. Local SQLite runs
with foreign-key enforcement off, so a bogus id wrote a row whose `category`
relationship resolves to `None`; `ProjectOut` / `ProfessionalOut` then failed
validation on the **next** `GET /projects` or `GET /professionals` call. One
crafted request could take down the public marketplace listing for everyone.
On Postgres this was a hard FK error (500) instead.

### Fix
- `create_project` (projects.py), `register_professional` and `become_talent`
  (auth.py), and `update_my_profile` (professionals.py) now check
  `db.get(Category, category_id)` and return 400 "Unknown category" before
  touching the database.

### Why it matters
An attacker-controlled 500 on public read endpoints; also silently corrupts
data in dev.

## 4. `update_project` let clients rewrite hiring/escrow state — `backend/app/api/v1/projects.py`

### Bug
`PATCH /projects/{id}` accepted `status`, `assigned_professional_id`, and
`progress` from any project owner. A client could mark a project `completed`
with no work done, or assign any professional without accepting a bid. The
frontend never calls this endpoint, so it was dead-but-dangerous surface area.

### Fix
`status`, `assigned_professional_id`, and `progress` are now stripped from the
update for non-admins (admin can still force these, e.g. `force_cancel_project`
uses its own endpoint anyway). Clients keep title/description editing.

### Why it matters
These fields are owned by the bid-acceptance and milestone state machines;
letting a free-form PATCH set them bypasses every invariant those flows
enforce.

## 5. Negative bid / milestone amounts — `bids.py`, `milestones.py`

### Bug
`BidCreate.amount` and `MilestoneCreate.amount` accepted anything, including
zero and negatives (e.g. a "bid" of -₦500,000, or a negative milestone amount
that would "refund" money on release).

### Fix
Both endpoints reject `amount <= 0` with 400.

### Why it matters
Negative amounts corrupt the ledger, the escrow math in `disburse_milestone`
and `refund_milestone`, and the client-facing "Payment Summary".

## 6. Email verification tokens stored raw — `backend/app/api/v1/auth.py`

### Bug
Password-reset tokens are stored as one-way hashes (`hash_token`) so a DB read
alone can't hijack an account, but email-verification tokens were stored **raw**
in `users.email_verification_token`. Anyone with DB access (or a leaked backup,
or a dump in dev) could verify any user's email.

### Fix
`_start_email_verification` now stores `hash_token(token)` (the raw token still
goes only into the emailed link), and `verify_email` looks up by
`hash_token(payload.token)`.

### Why it matters
Brings email verification in line with the project's own documented convention
("a DB read alone can't be used to ... verify their email"). The column shape is
unchanged (still a string), so no migration is needed. Outstanding old-style
links stop working; the user re-requests from settings, which is the intended
recovery path. Demo/seeded users are unaffected (they set `email_verified_at`
directly).

## 7. Client profile save clobbered derived flags — `backend/app/api/v1/clients.py`

### Bug
`PATCH /clients/me` returned the raw ORM user against `UserOut`, and
`UserOut.email_verified` / `has_professional_profile` are derived fields that
raw `model_validate` leaves at their defaults (`false`). After any client
profile save, the response told the frontend the client was unverified, which
could flip verification UI / role-switcher state on the next refresh of auth
state.

### Fix
Return `UserOut.from_user(current_user)`, same as `GET /auth/me`.

### Why it matters
Correctness of auth state the UI depends on; subtle, silent state corruption.

## 8. Admin registration edge cases — `backend/app/api/v1/admin.py`

### Bug
- Duplicate check used `User.email == payload.email` (case-sensitive) while
  every other registration path uses `ilike`. Creating `Admin@x.com` when
  `admin@x.com` exists slipped past the check and hit the DB unique constraint
  as a 500.
- The minted token omitted the `tv` claim (the token-version claim every other
  issuer includes), so token invalidation semantics were inconsistent for the
  very first admin created this way.
- Response used raw `model_validate`, same derived-fields issue as #7.

### Fix
`ilike` lookup, `tv` claim included, `UserOut.from_user`.

### Why it matters
Consistency and correctness of the account-bootstrap path.

---

## 9. Unhandled Monnify errors → 500s — `backend/app/api/v1/wallet.py`

### Bug
`topup_wallet`, `withdraw_wallet`, and `set_payout_details` call the Monnify
client without guarding failures. In simulated mode these short-circuit, but
once real keys are set, any network error, timeout, or Monnify 5xx surfaces as
an unhandled 500 (and in `withdraw_wallet` the user gets no usable error).
The webhook also did an unguarded `json.loads` on the raw body.

### Fix
- Monnify calls in all three endpoints are wrapped; failures return 400 with a
  friendly message ("Could not start payment", "Could not process the
  withdrawal", "Could not verify this bank account").
- Webhook body parse is guarded → 400 "Invalid JSON body".

### Why it matters
Graceful degradation was already the app's pattern everywhere else (email,
KYC); payments should not be the exception once real keys are live.

## Deliberately not changed (flag for a decision)

1. **Admin "force cancel" on a project with funded milestones** strands escrow
   money with no refund path (funds are still trackable in wallet transactions,
   and the client can still release a funded milestone on a cancelled project,
   which is itself odd). The clean fix is auto-refunding funded milestones on
   cancel. Left alone because it changes money behavior and the team should
   sign off on it.
2. **`FundWalletDialog` ignores the Monnify `checkout_url`** — in real (non-
   simulated) mode the UI would claim success before payment completes. Fine
   while payments are simulated; needs a redirect flow when real keys land.
3. **Free-text search fallback** returns *all* projects when a natural-language
   query matched a category but no listing exists in it. Intentional per code
   comments, flagged as a UX choice.
4. **`project.assigned_professional_id` / `status` remain writable through the
   admin path** of `update_project` — that's the intended oversight escape
   hatch; the dedicated cancel endpoint is preferred.

## Project-flow dead-ends pass (same session)

A walkthrough of the full journey (post job -> proposal -> accept -> milestones
-> escrow -> payout) surfaced three places users or projects could get stuck
with no way out. All three are fixed.

### 1. Milestone ownership: hired professionals can now propose milestones

**Before:** only the client could create milestones, but the bid-accepted
notification told the hired professional "You can now set up milestones and get
started." The promise was unreachable, and the work plan was entirely one-sided.

**After:**
- `Milestone.created_by` records who defined each milestone (new migration
  `b2c3d4e5f6a7`); the client and the assigned professional can both add them,
  admins too. The professional's proposal is badged "Proposed by <name>" in the
  workspace, with "fund to approve" for the client.
- Funding IS the approval gate: money only moves when the client funds a
  milestone, so a professional's proposal can never pull funds on its own. The
  client is notified when a professional proposes one.
- The acceptance notification copy now says exactly that: "You can now propose
  milestones for the client's approval and get started."
- Bonus fix: a milestone update now notifies the *other* party. Previously an
  update always notified the client, so a client's own note never reached the
  professional.

### 2. Project completion no longer dead-ends on refunds

**Before:** `disburse_milestone` completed a project only when *every* milestone
was `paid`. A milestone refunded via a dispute resolution never satisfied that
check, so the project stayed `in_progress` forever, progress could never hit
100%, and reviews stayed locked.

**After:**
- Completion now triggers when every milestone is in a terminal state (`paid`
  or `refunded`) and only transitions forward from an active status. `computed_progress`
  and the workspace progress bar count refunded milestones as closed, so a
  completed project reads 100%.
- New manual path for everything else: `POST /projects/{id}/complete` (client
  only) moves an in-progress project into final review. Guarded: blocked while
  an open dispute exists, and blocked if any milestone still holds escrow funds
  (`funded`/`approved`) so money is never stranded. The workspace got a "Start
  Final Review" action in Quick Actions for clients.

### 3. The client is notified when the project completes

**Before:** on auto-completion the professional got "Payout released" but the
client got nothing, and nothing nudged either party toward the review step.

**After:** both parties are notified when the project enters final review and
again when the client confirms completion (email for the client), with review
forms unlocked only after confirmation. See the Review-state pass below for the
full sign-off flow.

## Review-state pass: the final-acceptance window (same session)

The `review` project status existed in the enum and the UI (admin filter tab,
talent active-jobs list, badge color) but nothing ever transitioned into it, so
completion jumped straight from `in_progress` to `completed` with no sign-off
moment. Now it's the standard final-acceptance window.

### What happens now

- **Entering review:** when the last milestone is paid or refunded
  (`_maybe_complete_project`), the project lands in `review`, not `completed`.
  The manual client action (`POST /projects/{id}/complete`) also moves to
  `review` instead of completing. Both parties are notified (email): the client
  is told to do a final check and confirm; the professional is told to leave a
  closing note or flag remaining issues before sign-off.
- **Professional reply:** `POST /projects/{id}/closing-note` (assigned
  professional only, only while in `review`) stores `projects.closing_note`
  (migration `c3d4e5f6a7b8`), notifies the client, and appears in the client's
  review panel. Empty note clears it.
- **Client sign-off:** `POST /projects/{id}/confirm` (client only, only while
  in `review`, blocked by an open dispute) is the sole transition into
  `completed`; it sets `completed_at`, notifies both parties, and unlocks the
  review forms.
- **Reopen:** `POST /projects/{id}/reopen` (client only, from `review`) sends
  the project back to `in_progress` so more milestones can be added and funded
  (e.g. the professional's note surfaced a real remaining issue). The
  professional is notified.
- **Staleness fix:** the workspace now mirrors its `project` prop into local
  state, so status-affecting actions (accept proposal, start review, confirm,
  reopen, closing note) refresh the header status and the review panel in place
  instead of leaving the UI on a stale status until navigation.
